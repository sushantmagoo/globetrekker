# Globetrekker — Observability

One key user journey, **write and publish a journal**, is instrumented end to end with
metrics, traces and structured logs that share a trace id. No customer data or credentials
are sent to telemetry. The monitoring stack collects, stores and shows the signals in Grafana,
locally and in production.

```bash
make obs-up       # app + OpenTelemetry Collector, Prometheus, Loki, Tempo, Grafana
make obs-verify   # run the journey and check every signal arrived, linked and clean
make obs-down     # stop everything (keeps data)
```

| What | URL |
| --- | --- |
| Grafana (opens on the journey dashboard, no login) | <http://127.0.0.1:3000> |
| Prometheus (metrics) | <http://127.0.0.1:9090> |
| Loki (logs, API only) | <http://127.0.0.1:3100> |
| Tempo (traces, API only) | <http://127.0.0.1:3200> |

All ports bind to `127.0.0.1`. Locally `make obs-up` turns on passwordless Grafana. Everywhere
else Grafana requires a login (user `admin`, password `GRAFANA_ADMIN_PASSWORD`).

## Which compose files run where

| Environment | Command | Files (in order) |
| --- | --- | --- |
| Local, app only | `docker compose up` / `make up` | `docker-compose.yml` + `docker-compose.override.yml` (auto-loaded) |
| Local with monitoring | `make obs-up` | `docker-compose.yml` + `docker-compose.override.yml` + `docker-compose.observability.yml` |
| CI e2e | `docker compose up` | same as local, app only |
| Production (EC2) | `deploy/remote-deploy.sh` (CI runs it via SSM) | `docker-compose.yml` + `docker-compose.prod.yml` + `docker-compose.observability.yml` |
| Build prod images locally | `make build-prod` | same files as production |

- `docker-compose.override.yml` (dev images, hot reload, ports 5173/8000/5432) is **never** used in production. Compose only auto-loads it when no `-f` is given.
- `docker-compose.observability.yml` is the same file in both environments. Its defaults are the production-safe ones; `make obs-up` relaxes them for local use.
- `make check-compose` validates all three merged configurations.

## Production

The monitoring stack ships with every release. CI adds `docker-compose.observability.yml` and `observability/` to the release bundle, and the deploy script includes that file. What makes it safe to run there:

| Concern | How it's handled |
| --- | --- |
| Exposure | Every monitoring port binds to `127.0.0.1` and the security group only opens 80/443, so nothing is reachable from the internet. Use the SSM tunnel in [`deployment.md`](deployment.md#grafana-monitoring). |
| Grafana access | Login required (anonymous off, sign-up off). The password is the SSM parameter `GRAFANA_ADMIN_PASSWORD`, generated by `infra.yml`. The deploy fails early if it's missing. |
| The app must not depend on monitoring | The backend's dependency on the Collector is `required: false`. If the Collector is down, the API keeps serving and the SDK only logs export warnings (bounded by Docker log rotation). Rehearsed: stopping the Collector left the API healthy and answering in about 5 ms. |
| Memory | Limits: Collector 192 MB (its `memory_limiter` keys off that), Prometheus, Loki, Tempo and Grafana 384 MB each. Idle use is about 0.9 GB, so use a **t3.medium** (`INSTANCE_TYPE`). |
| Disk | All data lives in named volumes under Docker's data root on the encrypted `/data` volume, next to Postgres. Retention is 7 days everywhere, and Prometheus is also capped at 2 GB (`METRICS_RETENTION_SIZE`). Docker container logs rotate at 3 × 10 MB. |
| Persistence across deploys | Volumes are named (`globetrekker_prometheus` etc.), so dashboards' history and Grafana state survive releases. Dashboards and the alert are re-provisioned from the release's files. |
| Rollback to an old release | Bundles from before monitoring existed don't contain the file. The deploy script then runs without it, so rolling back still works. |

Rehearsal: the production file set (`prod` images, all three files) was started locally in an isolated project. Results:
- `make obs-verify`, run inside the network, passed every check.
- Grafana returned 401 without a login or with the wrong password, 200 with the configured one, and was unreachable from the LAN address.

**Changing the Grafana password later.** `GF_SECURITY_ADMIN_PASSWORD` only applies when Grafana's database is first created. Afterwards, update the SSM parameter and run on the instance: `dc exec grafana grafana cli admin reset-admin-password '<new>'`.

## Architecture

```
FastAPI backend ──OTLP/HTTP──> OpenTelemetry Collector ──> Prometheus (metrics)
 (be/app/core/telemetry.py)     (scrubs again, batches)  ──> Loki       (logs)
                                                          ──> Tempo      (traces)
                                                                 │
                                                              Grafana
```

- **Backend:** the OpenTelemetry Python SDK, set up in `be/app/core/telemetry.py`. It only exports when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, which `docker-compose.observability.yml` does. Without it (plain `make up`, tests, CI) spans still get real trace ids, so stdout logs stay correlated, but nothing is sent anywhere.
- **Config:** everything else lives in `observability/`: the Collector, Prometheus, Loki and Tempo configs, Grafana provisioning, the dashboard and the alert rule.
- **Same versions as hw4:** Collector contrib 0.131.0, Prometheus 3.13.5, Loki 3.5.3, Tempo 2.8.2, Grafana 12.1.1.

## The journey

| Step | Request | Span name | What else is recorded |
| --- | --- | --- | --- |
| `create_draft` | `POST /api/v1/journals` | `POST /api/v1/journals` | log `journal draft created` |
| `autosave` | `PATCH /api/v1/journals/{journal_id}` | `PATCH /api/v1/journals/{journal_id}` | child span `journal.render` (word count); log `journal autosaved`, or `journal autosave conflict` (409) |
| `publish` | `POST /api/v1/journals/{journal_id}/publish` | `POST /api/v1/journals/{journal_id}/publish` | counter `journals.published` by visibility; log `journal published`, or `journal publish rejected` (422, lists the missing fields) |
| `read` | `GET /api/v1/journals/{slug}` | `GET /api/v1/journals/{slug}` | span attributes: whether a share link was used and whether the reader is signed in |

Every step's server span has `journey=publish_journal` and `journey.step=<step>`, plus SQL child spans from the SQLAlchemy instrumentation (parameterised statements only).

### Signals

**Metrics** (Prometheus names):

| Metric | Labels | Purpose |
| --- | --- | --- |
| `journey_step_requests_total` | `journey_step`, `outcome` (`success`/`client_error`/`server_error`), `http_response_status_code`, `error_type` | Funnel and error rates per step |
| `journey_step_duration_seconds` | same | Latency per step, with **exemplars** (trace ids) |
| `journals_published_total` | `journal_visibility` | Business outcome |
| `http_server_request_duration_seconds` | `http_route`, `http_request_method`, `http_response_status_code` | Every API route, not just the journey |

**Traces:** one server span per API request (every route, not only the journey), with SQL spans and `journal.render` underneath.

**Logs:** structlog events, printed to stdout and also sent as OTel log records. Each record carries:
- `trace_id` and `span_id` of the active span (Loki stores them as structured metadata);
- the `request_id`;
- the event's own fields.

Every API request also writes one `request` log line with the route, status and duration.

### How the signals link up

- **Log → trace.** Loki's `trace_id` field links to Tempo.
- **Trace → logs.** Tempo's "Logs for this span" button runs a Loki query on the trace id.
- **Metric → trace.** On the latency panel, each dot is an exemplar; click it to open that request's trace.
- **Tests guard the links.** `be/tests/integration/test_telemetry.py` checks that a step's log records, server span and latency exemplar share one trace id.

## Dashboard and alert

**Globetrekker - Publish a journal** (Grafana's home page) has three parts:
- **Stats:** drafts started, autosaves, journals published, publish success rate, journey 5xx and publish p95 latency.
- **Charts:**
  - requests per step by outcome;
  - latency p50/p95 with exemplars;
  - failed steps by status code (409 conflicts, 422 rejections, 5xx);
  - published journals by visibility.
- **Traces and logs:** a recent-traces table (TraceQL `{ span.journey = "publish_journal" }`), journey logs, and all backend warnings and errors.

A **Step** variable filters the charts to one or more steps.

**Alert: Users failing to write or publish journals.** This is a user-impact alert: it fires when, for any journey step, more than 5% of requests fail with a 5xx over 5 minutes *and* at least 3 requests failed. That must hold for 1 minute; no traffic counts as Normal. The SLO is 99% of journey requests succeeding.
- Each step alerts separately (`journey_step` label).
- The summary says how many users were hit, for example `34% of "publish" requests are failing`.
- Every alert goes to the **on-call agent** webhook, which collects the evidence and runs a coding agent to fix the issue.

See [`on-call-agent.md`](on-call-agent.md) for the rule's reasoning, the agent and the end-to-end drill.

## Privacy: what is never sent

Two layers enforce this. The first is in the app (`be/app/core/telemetry.py`):

| Rule | How |
| --- | --- |
| No raw URLs | Spans, metrics and logs use the **route template** (`/api/v1/journals/{slug}`), never the path (which contains the slug, derived from the title) or the query string (which contains share tokens). |
| No headers, cookies, client IPs or bodies | The custom middleware never reads them. |
| No user identifiers or journal text | Telemetry has no user id, username, email, display name, title, subtitle or content. The only identifier is the opaque journal UUID. |
| No exception messages | Unhandled errors record `error.type` (the class name) and `exception_frames` (code locations: `file:line in function: source line`, with emails and tokens masked) but never the message or local variables, which can quote user input. |
| No SQL values | DB spans hold the parameterised statement (`WHERE users.id = $1`). Bound values are never recorded. |
| Scrubbing for everything else | Every log event and custom span attribute goes through `scrub()`. It drops keys like `password`, `token`, `cookie`, `email`, `username`, `title`, `content` and `bio`, and masks values that look like emails, JWTs or `Bearer …` headers. |
| FastAPI's built-in telemetry is off | FastAPI 0.163 turns on its own OpenTelemetry as soon as SDK providers exist. It would record `url.path`, `url.query`, exception messages and rejected input values (e.g. a too-short password), so `main.py` disables it. |

The second layer is in the Collector (`observability/otel-collector.yaml`). Its `transform/scrub` processor:
- deletes the same kinds of attribute keys again;
- deletes `exception.message` and `exception.stacktrace`;
- masks emails and JWTs in attribute values and log bodies.

This catches leaks from future code before they reach storage.

**How it's tested:**
- **Unit** (`tests/unit/test_telemetry.py`): scrubbing rules, and logs carrying the current trace id.
- **Integration** (`tests/integration/test_telemetry.py`):
  - The test runs sign-up, the whole journey (unlisted, read via share link), login and a token refresh. It then searches every exported span, span event, log record and metric label for the password, email, username, display name, access token, refresh cookie, share token, title, text and slug. None may appear.
  - A forced 500 whose exception message contains an email must not leak it.
  - Mutation check: turning FastAPI's native telemetry back on makes this test fail (share token and slug leak).
- **Against the real stack** (`make obs-verify`): runs the journey, then reads back from Tempo, Loki and Prometheus to check that:
  - each step has a trace, logs and metrics;
  - the trace ids match;
  - exemplars point at the traces;
  - none of the user's secrets appear in the stored traces, logs or metric labels.
- **Collector scrubbing** was checked by posting a log with an email, a `user.password` attribute, a JWT and an exception message straight to the Collector. Loki stored `[REDACTED]` for the email and JWT, and dropped the other two keys.

## Configuration

| Variable | Default | Effect |
| --- | --- | --- |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | unset | Where to send OTLP. Unset means no export. |
| `OTEL_SERVICE_NAME` | `globetrekker-backend` | `service.name`, which becomes the Prometheus `job` and the Loki `service_name` |
| `OTEL_METRIC_EXPORT_INTERVAL` | `60000` (stack: `15000`) | Metric push interval in ms |
| `OTEL_CONSOLE_EXPORT` | `false` | `true` also prints all signals to the backend's stdout |
| `GRAFANA_ADMIN_PASSWORD` | required | Grafana `admin` password (prod: SSM parameter; `make obs-up`: `admin`) |
| `GRAFANA_ANONYMOUS` | `false` | `true` = passwordless admin, set only by `make obs-up` |
| `METRICS_RETENTION`, `METRICS_RETENTION_SIZE` | `7d`, `2GB` | Prometheus retention |
| `GRAFANA_PORT`, `PROMETHEUS_PORT`, `LOKI_PORT`, `TEMPO_PORT`, `OTEL_GRPC_PORT`, `OTEL_HTTP_PORT` | 3000, 9090, 3100, 3200, 4317, 4318 | Host ports (127.0.0.1 only) |

Each uvicorn worker reports its own `service.instance.id`, which Prometheus turns into the `instance` label. Dashboards sum across instances.

Retention: Prometheus 7 days, Loki 7 days, Tempo 7 days.

## Not covered yet

- **Not yet run on real AWS:** the production setup was rehearsed locally, not on EC2. The monitoring data shares one instance and volume with the app, so losing the instance loses recent telemetry. If that matters, a managed backend such as Grafana Cloud only needs `OTEL_EXPORTER_OTLP_ENDPOINT` and headers.
- **Frontend:** no browser tracing yet, so a trace starts at the API rather than at the click. Adding it needs the browser OTel SDK and `traceparent` propagation, which the backend doesn't accept yet.
- **Other journeys:** only this journey has dedicated metrics. Every route still gets server spans, `http_server_request_duration_seconds` and request logs.
- **Human paging:** the alert goes to the on-call agent only; there's no Slack or email contact point yet.
